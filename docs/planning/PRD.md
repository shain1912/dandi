## 1. 기획 의도 (Rationale & Background)

- **바이브코딩의 대중화와 교사의 한계 극복**
  - 최근 AI 코딩(Cursor, Claude 등)을 활용한 '바이브코딩'으로 교사들이 자신만의 교육용 웹 앱이나 대시보드를 뚝딱 만들어내는 사례가 폭발적으로 늘고 있다. 하지만 이 훌륭한 결과물들이 개별 로컬 환경이나 흩어진 링크로만 남아 있어 **동료 교사들과 공유되고 재사용되기 어려운 문제점**이 있다.
  - 교사단에서 공유된 사례만 보아도 로컬 작곡 프로그램, 시험 범위 학습 사이트, 교과서 선정 서류 생성기(한 교사 제작), 한 중학교 교사들의 업무 간소화 앱 등이 각각 따로 만들어지고 있다.

- **압도적으로 단순한 개발·배포 경험 (CLI 중심)**
  - 교사들은 바쁘다. 복잡한 클라우드 설정, 웹 패널 로그인, Git 명령어 지옥을 겪을 시간이 없다.
  - 터미널 환경에서 명령어 한 줄(CLI) 또는 초간단 터미널 로그인만으로 프로젝트를 생성하고, 즉시 Vercel과 Supabase에 배포 및 연동이 끝나는 **개발자 친화적이면서도 극도로 단순한 워크플로우**가 필요하다.
  - 교사가 **비용 없이** 배포까지 마칠 수 있어야 한다(인프라 비용 주체는 12장 Q7).

- **로그인 허들 없는 학생·사용자 경험 (토스 미니앱 모델)**
  - 학생들이나 학부모, 동료 교사가 미니앱을 쓰거나 자료를 다운로드할 때 회원가입 창이 뜨는 순간 이탈률이 급증한다.
  - 토스 미니앱처럼 **접속 즉시 익명 세션(Anonymous Auth)으로 앱을 곧바로 실행**하고, 필요한 응용 프로그램(`.exe`, `.zip`)과 강의 자료를 무로그인으로 빠르게 내려받을 수 있는 구조를 지향한다.

- **안심하고 공유하는 신뢰성 (보안 & 개인정보 필터링)**
  - 학교 현장에서 가장 민감한 문제는 개인정보 유출이다. 커뮤니티나 미니앱 입력 폼에 학생들의 정보나 연락처가 실수로 노출되지 않도록, **시스템 레벨에서 자동으로 개인정보를 필터링하고 마스킹**하여 교사들이 안심하고 지식과 앱을 공유할 수 있는 안전지대를 만든다.
  - 필터링만으로는 부족하다. 운영위원회 등 학교 내부 심의 전에 개인정보 쟁점을 미리 점검할 수 있도록, **배포 전에 개인정보 처리 여부를 스스로 점검하는 절차**를 플랫폼이 안내하고, 내부 승인이 필요한 앱은 승인 전까지 공개하지 않는다.

- **교사를 지원하는 AI, 스스로 만드는 교사**
  - 학생이 AI에 과제를 맡기면 학습 효과가 떨어진다는 우려가 있어(OECD 경고 기사 공유), AI는 교사를 지원하는 도구로 사용하자는 제안이 나왔다.
  - 작업 지시서와 예시 사이트를 보고 교사가 직접 만들어 보는 경험을 늘리고, 동시에 배포·API·보안을 떠받치는 **플랫폼 역량**도 함께 갖춘다.

## 2. 핵심 구현 전략: "초간단 CLI & 무로그인 미니앱"

### ① CLI 및 개발자 경험 (CLI First & Simple Login)

- **터미널 로그인 한번으로 끝:** 복잡한 웹 대시보드 로그인 대신, 터미널에서 명령어(`dandi login` 등) 한 번 실행으로 브라우저 연동 인증을 거치거나 토큰 하나로 세션이 유지되도록 설정.
- **원클릭 배포 스크립트:** 코딩이 끝나면 터미널에서 명령어 입력만으로 `llms.txt` 기반 프로젝트가 빌드되고 Vercel 배포와 Supabase DB 연동이 동시에 완료되는 CLI 툴링 제공.

### ② 토스형 무로그인 (Anonymous-First UX)

- 사용자가 링크를 눌러 들어왔을 때 로그인 페이지를 강제하지 않음.
- Supabase 익명 인증을 백그라운드에서 자동 처리하여, **로그인 없이 미니앱 구동, 커뮤니티 글 읽기, 자료 다운로드**를 1초 만에 수행.

### ③ 개인정보 자동 필터링 (Zero-Leak Policy)

- 클라이언트(입력창)와 서버(API) 양쪽에서 정규식 및 PII 검사기를 상시 구동하여, 주민번호·전화번호·이메일 등 민감 정보 입력 시 즉시 차단 및 자동 마스킹.
- 앱을 등록할 때 개인정보 셀프점검 5개 항목을 모두 작성해야 하고(합격·불합격 판정 없음), 앱 카드에 답변 요약을 배지로 표시.
- "학교 내부 승인 필요"로 답한 앱은 승인 완료 전까지 **승인 대기** 상태로 두어 허브 목록과 무로그인 실행에서 제외.

### ④ 작업 지시서 기반 학습 (Template First)

- "샘플 + 작업 지시서"를 한 쌍으로 제공. 교사는 예시 사이트를 먼저 실행해 보고, 작업 지시서를 복사해 AI 코딩 도구에 붙여 넣어 자기 버전을 만든다.
- 개발부터 배포까지 따라 할 수 있는 단계별 안내, 스킬 파일, 디자인 명세(`DESIGN.md`) 예시, Supabase·Vercel MCP 연동 가이드를 함께 제공한다. 조현식은 "결국 마지막 1%를 좌우하는 것은 디자인"이라고 했다.

### ⑤ AI 모델 게이트웨이 & 정책 (Policy-Governed AI)

- 교사에게 일정 한도의 API 키를 무상으로 지급하고, 모든 호출은 플랫폼 게이트웨이를 거친다.
- 게이트웨이는 **교육청 관리자가 허용한 모델만** 통과시키고, 프롬프트에 섞인 개인정보를 호출 전에 가린다.
- 모델마다 제공사, 실행 방식(온라인 API / 로컬·온프레미스), 데이터 처리 위치, 권장 용도를 표시해 교사가 용도에 맞게 고르도록 안내한다. 가이드 내용은 교육청 관리자가 입력·승인한다.

## 3. 개요 (Overview)

- **목적:** 교사들이 AI(바이브코딩)를 통해 생성한 교육용 미니앱, 대시보드, 강의 자료를 손쉽게 배포하고, 학생 및 동료 교사와 공유할 수 있는 통합 커뮤니티 및 다운로드 플랫폼 구축.
- **타겟 유저:**
  - **교사(크리에이터):** 코딩 지식이 깊지 않아도 AI로 미니앱과 강의 자료를 만들어 올리고 공유하는 사람. 초·중·고·특수 학교급 구분. 10월 연수 참여 교사 포함.
  - **학생/일반 사용자:** 별도의 복잡한 회원가입 없이 미니앱을 즉시 이용하고, 필요한 응용 프로그램 및 자료를 다운로드받는 소비자.
  - **교육청 관리자:** AI 모델 허용 정책과 모델 가이드를 관리하고 감사 로그를 확인하는 담당자(장학사 등). API 한도 설정은 v1.0(F-28).

## 4. 핵심 목표 및 가치 (Key Objectives)

- **초간단 배포 및 버전 관리:** GitHub와 Vercel 연동으로 코딩 결과물을 원클릭 수준으로 라이브 배포 및 이력 관리(배포 이력 관리는 F-30).
- **무로그인 사용자 경험 (토스 미니앱 모델):** 익명 인증(Anonymous Auth)을 도입해 이용자는 로그인 허들 없이 앱을 즉시 실행.
- **안전한 커뮤니티 & 자료실:** 3중 개인정보 필터링 시스템(클라이언트 필터 · 서버 마스킹 · RLS)을 통해 안심하고 글과 응용 프로그램(`.exe`, `.zip`, `.pdf`)을 공유.
- **AI 개발 가속화:** `llms.txt` 및 MCP(Model Context Protocol) 지원으로 AI 코딩 도구(Cursor, Claude)가 프로젝트 구조를 완벽히 이해하고 개발 지원(F-12).
- **교사 비용 0원:** 배포와 AI API 사용에 교사 개인 비용이 들지 않도록 무상 한도 제공(인프라 비용 주체는 Q7).
- **정책 준수 AI 사용:** 교육청이 정한 모델 정책을 플랫폼이 강제해, 교사가 규정 위반을 걱정하지 않고 AI를 사용.
- **스스로 만드는 교사:** 작업 지시서 + 예시 사이트로 교사의 직접 개발 경험을 늘림.

## 5. 유저 스토리 (User Stories)

- **교사 A:** "바이브코딩으로 만든 학급 출석 미니앱을 Vercel에 올리고, 동료 교사들과 공유하기 위해 커뮤니티에 다운로드 링크와 설치 파일을 올리고 싶다."

- **시스템 관리자:** "커뮤니티 게시글이나 입력 폼에 사용자가 실수로 전화번호나 주민등록번호를 적었을 때, 시스템이 자동으로 차단하거나 마스킹해주기를 원한다."

- **고등학교 교사 D:** "교과서 선정 서류처럼 반복되는 업무 문서를 hwpx로 뽑아 주는 사이트를 동료에게 공유하고, 우리 학교급 교사들이 올린 업무용 앱만 모아 보고 싶다."
- **교사 E (학생지도 앱 제작):** "학생 정보를 다루는 앱을 만들었는데, 공개하기 전에 개인정보 측면에서 무엇을 확인해야 하는지 체크리스트로 점검하고, 학교 내부 승인이 나면 공개하고 싶다."
- **교사 F:** "AI API를 비용을 들여 구매해 사용해 왔다. 학교 업무용이라면 플랫폼이 주는 키로, 허용된 모델 중 용도에 맞는 것을 골라 사용하고 싶다."
- **교육청 관리자 G:** "어떤 AI 모델을 허용할지는 교육청 정책으로 정해야 한다. 정책이 정해지면 관리 화면에서 모델별 허용·보류·차단을 바꾸고, 교사 화면과 API 호출에 바로 반영되기를 원한다."

## 7. 비기능 요구사항 (Non-Functional)

- **개인정보:** 학생 개인정보는 기본적으로 저장하지 않는다. 저장하는 모든 텍스트 입력은 서버 마스킹을 거친다. 업로드 파일은 작성자 확인(F-08)으로 대신하고 내용 검사는 P2.
- **비용:** 교사 1인당 배포·AI 사용 비용 0원(무상 한도 내, 인프라 비용 주체는 Q7).
- **성능:** 앱 카드 클릭부터 미니앱 실행까지 1초 내외(임베드 로딩 제외).
- **접근성:** CLI(F-17~F-19)를 제외한 모든 P0 웹 기능을 모바일 브라우저에서 사용 가능.
- **감사 가능성:** 모델 정책 변경, API 키 발급, 파일 업로드, 앱 등록·승인을 기록하고 관리자가 조회(F-27).
- **이식성:** 프로토타입의 저장소 계층은 Supabase로 교체할 수 있도록 인터페이스를 분리한다.

## 8. 기술 스택 (Tech Stack)

- **Frontend & Hosting:** Next.js (App Router), Vercel
- **Backend & DB:** Supabase (PostgreSQL, Realtime, Edge Functions)
- **Storage:** Supabase Storage (앱 및 파일 호스팅)
- **Version Control:** GitHub
- **AI Gateway:** Next.js Route Handler(프로토타입) → Supabase Edge Function 또는 별도 게이트웨이(v1.0)
- **프로토타입(v0.1) 대체 목록:** 외부 계정 없이 로컬에서 바로 실행되도록 다음으로 대신한다. 저장소 계층만 교체하면 Supabase로 옮길 수 있게 만든다.
  - 익명 인증 → 브라우저 세션 쿠키
  - 소셜 로그인 → 데모 로그인(이름·역할·학교급)
  - PostgreSQL·RLS → 로컬 JSON 저장소·서버 코드 작성자 검사
  - Supabase Storage → 로컬 파일 저장소
  - 실제 AI 모델 → 모의 응답

## 9. 화면 구성안 (UI/UX Wireframe Flow)

```text
[메인 대시보드 (Hub)]
 ├── 상단: 인기 미니앱 바로 실행 (무로그인 / 토스형 UX)
 ├── 중단: 커뮤니티 피드 (강의 자료, 질문, 정보 공유)
 ├── 하단: 응용 프로그램 다운로드 섹션 (.exe / 자료실)
 └── 전역: 학교급 필터 (전체 / 초 / 중 / 고 / 특수)

[데모 로그인 / 계정]
 └── 이름 · 역할(교사/관리자) · 학교급 선택, 로그아웃

[미니앱 목록 · 실행]
 ├── 학교급 · 분류 필터, 개인정보 배지
 ├── 임베드 실행 + 새 창 열기
 └── 셀프점검 답변 전체

[커뮤니티]
 ├── 목록: 학교급 · 분류 필터
 ├── 글쓰기 (실시간 개인정보 경고)
 └── 글 보기: 좋아요(무로그인), 댓글, 작성자 삭제

[자료실]
 ├── 목록: 학교급 필터, 다운로드 수

[템플릿 갤러리]
 ├── 작업 지시서 + 예시 사이트 카드, 학교급 · 분류 필터
 ├── 작업 지시서 복사 / 예시 실행
```

## 10. 범위 제외 (Non-Goals)

- 플랫폼이 AI 모델 허용 여부를 스스로 판단하지 않는다. 허용 여부는 교육청 정책을 따른다.
- 연수용 카카오톡 방 개설·운영은 플랫폼 범위가 아니다. 다만 플랫폼 게시판은 학교급 태그·필터로 통합 운영과 학교급별 열람을 모두 지원한다.
- 교사 앱의 코드 품질을 심사하지 않는다. 셀프점검은 합격·불합격을 판정하지 않고 작성만 요구한다.
- 운영위원회 등 학교 내부 승인 절차를 대체하지 않는다. 플랫폼은 승인이 필요한 앱을 승인 완료 표시 전까지 공개하지 않을 뿐이다.
- v0.1은 교사 앱을 대신 배포하지 않는다. 교사가 배포한 외부 URL을 등록한다.

## 15. v0.2 확장 기능 요구사항

우선순위 표기는 6장과 같다. P0은 v0.2 프로토타입에 넣는다.

### ⑩ AI 에이전트 연결 (Agent Connect)

| ID | 기능 | 설명 | 우선순위 |
|---|---|---|---|
| F-51 | 허브 정적 호스팅 | 교사가 만든 정적 사이트 폴더를 허브가 직접 호스팅한다. `deploy`는 **비공개 미리보기**를 만들고, `publish`는 셀프점검(F-16)을 거쳐 허브에 미니앱으로 등록한다(힉스필드 deploy·publish 분리). 사이트는 허브와 다른 origin에서 서빙한다(로컬 `http://<slug>.localhost:3000`, 운영은 별도 도메인). 업로드는 3단계(파일 목록 → 파일 전송 → 확정), 배포는 불변 버전으로 저장하고 현재 버전 포인터만 바꾼다. 한도: 합계 20MB, 파일 1,000개, 파일당 5MB, 루트 index.html 필수, 확장자 허용 목록, 비밀값 패턴 거부 | P0 |
| F-52 | 웹 폴더 업로드 | 셸이 없는 교사를 위해 브라우저에서 폴더를 끌어다 놓아 F-51과 같은 흐름으로 올린다 | P0 |
| F-53 | CLI 브라우저 승인 로그인 | device code 방식. `dandi login`이 승인 링크와 8자리 코드를 보여 주고, 교사는 허브에서 코드가 같은지 확인한 뒤 [승인]한다. 에이전트나 비대화형 환경에서는 링크·코드를 JSON으로 출력하고 끝나며 `login --wait`로 이어서 기다린다. 코드는 10분 만료·1회용, 승인 화면에 요청 에이전트·컴퓨터 이름·시각과 피싱 경고를 표시한다. 토큰을 채팅에 붙여 넣는 과정이 없다 | P0 |
| F-54 | 에이전트 친화 CLI | 모든 명령에 `--json`, 원인별 종료 코드(4 로그인 필요, 5 승인 대기, 6 거부, 7 만료, 20 업로드 거부), 오류마다 다음 명령 안내, `dandi guide`(런북 원문 출력). npm 공개 전에는 허브가 `dandi-<버전>.tgz`를 제공하고 `npx -y <허브>/dandi-<버전>.tgz <명령>`으로 설치 없이 실행한다 | P0 |
| F-55 | `/llms.txt` 실행 런북 | AI 에이전트가 읽고 그대로 따라 하는 "내 사이트 올려줘" 절차(5KB 이하). 셀프점검 5문항은 반드시 교사에게 묻고, 토큰·비밀번호를 채팅에 요구하지 않는다는 금지 규칙을 포함한다. `/llms-full.txt`는 명령·JSON·종료 코드·MCP 설정 전체 레퍼런스. 허브의 `/llms.txt`(허브 사용 런북)와 교사 프로젝트 루트의 `llms.txt`(F-12, 프로젝트 명세서)는 역할이 다르며, 원본 PRD의 llms.txt 표준화 요구를 따라 이름은 그대로 둔다 | P0 |

F-61·F-62 시험 결과(2026-09-29): Grok 1.0.30과 Antigravity CLI 1.2.12가 "URL만 주기", "URL과 답을 함께 주기", "스킬 설치 후 주소 없이 요청하기" 세 시나리오를 모두 통과했습니다. 시험 중 Grok이 승인 링크만 보여 주고 끝나는 문제와 Grok이 신뢰하지 않은 폴더의 스킬을 읽지 않는 문제를 찾아 런북·스킬(1.3.1)·문서에 반영했습니다. Dandi를 모르는 Claude(서브에이전트와 `claude -p`)도 같은 시나리오와 비밀 키가 든 사이트 시나리오를 통과했습니다. Codex는 이 PC의 로그인이 만료되어 다시 로그인한 뒤 시험합니다. 자세한 기록은 [`docs/agent-trials-20260929.md`](../agent-trials-20260929.md)에 있습니다.
